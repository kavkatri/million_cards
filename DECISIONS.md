# Decisions, assumptions, and what's left

## Answered

| Question | Answer |
|---|---|
| Marketplace scope | Wildberries only, behind a clean adapter seam |
| Line definition | Full no-code builder in the UI |
| Deployment | Not the current production server; a separate host |
| Migration | None — the existing scripts keep running, this is greenfield |
| Parallelism | Many accounts at once, **and** many workers on one account |

## Assumptions made where the question was still open

Each is cheap to change; none is baked into the schema.

1. **Aspects are card / media / price / stock.** Descriptions, characteristics,
   barcodes, KIZ marking, promos and competitor repricing are not implemented.
   The `Aspect` enum plus a handler is the extension point.
2. **Stock is a constant per line** (`{"type": "constant", "value": 1000}`) and
   needs a `warehouse_id`. Real inventory would be another `stock_rule` type.
3. **Prices are formula-driven**, not imported from 1C or a spreadsheet.
4. **One shared login, all users equal.** `User.is_admin` exists but nothing
   branches on it yet.
5. **Russian-only UI.**
6. **Media and Content are separate rate-limit buckets.** The spec gives them
   separate tables ("для всех методов Медиафайлов" vs "…Контента") but does not
   state outright that the budgets are independent. If persistent 429s appear on
   media while content is busy, merge them in `app/marketplace/wb/limits.py` —
   it is a one-line change to `_ROUTES`.
7. **Notifications are not built.** Structured logs are emitted; no Telegram or
   email sink yet.

## Deliberate design choices

**Postgres for the queue, Redis only for rate limits.** The task table is already
the audit trail — what was attempted, how often, why it failed. Keeping the queue
in the same transactional store means a claim and its state change cannot
disagree after a crash. Redis holds only limiter state, where loss on restart is
harmless.

**No `eval` for price formulas.** The expression is parsed with `ast` and walked
against an allow-list. A price field typed in a browser is executed by a worker
holding credentials that can rewrite the whole catalogue.

**`withPhoto` stays `-1`.** Per the API docs, `0` has meant "any card" since
16 June, and `2` returns only cards with *zero* photos. `2` looks like the right
filter for "needs images" but silently excludes cards left part-way through by a
failed upload — in the live catalogue, 27 such cards. Completeness is judged by
counting `photos`, which WB omits entirely when empty.

**Card creation does not set `nm_id`.** Creation is asynchronous and the id is
not known yet; guessing would make the next reconcile believe the card exists.
Only `card_created_at` is stamped, which both records the attempt and holds the
SKU out of the price and stock aspects until the documented 30-minute sync window
passes.

**Quota is read, not assumed.** `GET /content/v2/cards/limits` returns the real
remaining allowance. Tiers are 1000/2000/5000, so a hardcoded constant is wrong
for someone.

**The initial migration calls `create_all`.** A hand-transcribed copy of an
eleven-table schema is a place for the migration and the models to silently
diverge. Later migrations are ordinary autogenerated diffs against this baseline.

**One run per line, enforced in the database.** Not a filesystem lock: that holds
only within a host and survives a crash as a stale file.

## Not yet built

- **Notifications** (Telegram/email) on failure and daily summary.
- **`cards/error/list` polling.** The adapter method exists and is tested, but no
  aspect calls it yet, so cards that fail asynchronously after a `200` are not
  yet surfaced. This is the most valuable next piece.
- **Price task confirmation.** `POST /api/v2/upload/task` is asynchronous;
  `GET /api/v2/history/tasks` should be polled to confirm rather than assuming
  submission means success.
- **Quarantine detection** — a discount ≥3× below the old price silently keeps
  the old price. `GET /api/v2/quarantine/goods` should feed a warning.
- **`QuotaUsage` is written but not yet consumed** for cross-line budgeting;
  planning currently reads live quota per run. With several lines on one account
  they should draw from a shared daily ledger.
- **Drag-to-position** in the image editor — coordinates are numeric inputs with
  a live preview; the canvas drag interaction is not implemented.
- **Retry/cancel controls** for failed tasks in the UI (the API exposes the data).
- **A real integration test against the sandbox.** The suite is unit-level; the
  sandbox makes an end-to-end test feasible and it should exist before the first
  production line.

## Open questions

These change design rather than configuration, so they are worth answering before
the system carries real volume.

1. How many lines in 12 months, and how many seller accounts? Catalogue sync is a
   full pass per line per run — at many lines this needs incremental sync via the
   `updatedAt` cursor rather than a full scan.
2. Are there non-grid SKUs that must live here, or is everything generated?
3. Should prices ever come from outside (1C, spreadsheet) rather than a formula?
4. Real warehouse stock, or is a constant genuinely enough?
5. Who else uses this, and do they need restricted permissions?
